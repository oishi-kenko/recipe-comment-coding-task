# 設計メモ

レシピコメント生成 API の設計判断と、その理由をまとめる。

## 1. 全体方針

ユーザーの属性（主に病態・料理スキル）に応じて、レシピのおすすめコメントを出し分ける。
BMI も検討したが、今回は病態と重複が多いと判断したためカテゴリには使わない（2.4 参照）。

リアルタイムで LLM を呼ぶとコストと遅延の問題があるため、コメントは事前生成して CSV に保存し、
リクエスト時は CSV を引くだけにする。事前生成の対象を絞るために、ユーザーをカテゴリに分類する。

## 2. ユーザーのカテゴリ設計

### 2.1 病態カテゴリ（6グループ + general）

`concern_name` は全20種類あり、そのまま全部を別カテゴリにすると、

- カテゴリ数が増えすぎて事前生成のコストが膨らむ
- 1人しかいない病態のために専用コメントを作るのは見合わない

という問題がある。そこで「病名」ではなく「**コメントで伝えたい栄養メッセージ**」を基準に束ねた。
同じレシピに対して出したいコメントがほぼ同じになる病態は、同じグループにまとめている。

| カテゴリ | まとめた病態 | コメントで伝えたいこと |
|---|---|---|
| 減塩 | 高血圧 / 血圧が高い / 心筋梗塞 / 心不全 | 塩分控えめ |
| ダイエット | ダイエット | カロリー控えめ・高たんぱく（前向きな応援トーン） |
| 脂質 | 脂質異常症 / コレステロールが高い / 中性脂肪が高い | 脂質・コレステロール控えめ（管理トーン） |
| 血糖 | 糖尿病（2型） / 糖尿病予備群 | 血糖値を上げにくい |
| 貧血 | 貧血対策 / 妊娠中（後期） | 鉄分などをしっかり |
| 便秘 | 慢性便秘症 | 食物繊維をしっかり |
| general | 健康的な食生活・病気予防 / ニキビ・肌荒れ / その他 | 特別な制限なし・バランス |

ダイエットと脂質は「低脂質」という共通点はあるが、ダイエットは「なりたい自分」、脂質異常症は
「管理すべき数値」で、コメントのトーンが違うと考えて分けた。

### 2.2 安全のために general へ固定する病態

透析 / CKD / 腎機能の値が高い / 逆流性食道炎 / 潰瘍性大腸炎 は、専用カテゴリを作らず、
分類の段階で必ず general に倒している。理由は安全性である。これらは「制限」が中心の病態で、
たとえば腎臓病はたんぱく質を控えることが多い。にもかかわらず LLM に専用コメントを書かせると、
ダイエット向けのような「高たんぱくでヘルシー」という、その人にとって逆効果のコメントを
自信を持って書いてしまうリスクがある。少数（各1〜2名）でもあるため、専用コメントを作る
メリットよりリスクが上回ると判断し、無難な一般コメントに寄せた。

### 2.3 料理スキルの扱い

当初はスキルもカテゴリにする（初心者向け／上級者向け）案を考えたが、やめた。理由は2つある。

- レシピが簡単か難しいかは、レシピの手順数や材料を LLM が見れば判断できるので、ユーザーを
  スキルで分けなくても、コメント側に自然に表れる。
- 上級者は何でも作れるので、上級者向けの特別なコメントは不要。必要なのは「料理に不慣れな人に、
  簡単なレシピのときだけ手軽さを伝える」ことだけ。

そこでスキルはカテゴリにせず、「初級・初心者ユーザー かつ そのレシピが簡単なときだけ、
手軽さの一言を添える」という扱いにした。カテゴリ数を増やさずに、必要な出し分けだけを実現している。

`classify_user` の返り値は `病態__スキル` 形式（例: `減塩__easy`）だが、CSV のキーは病態名
（`減塩` 等）と `general` / `beginner`。API 参照は病態部分のみ使い、スキル差は `beginner` の
有無で表現する。

### 2.4 BMI の扱い

BMI を分類に使うと出し分けの効果が小さいと判断し、今回は使用しなかった。BMI が高い層に向けたコメントは
結局「カロリー控えめ」が中心になり、病態のダイエットカテゴリと役割が重複するためである。
また BMI は連続値で、カテゴリにするには区切りの基準を別途決める必要もある。
そのため新たな軸を増やすより既存の病態カテゴリでカバーできると考え、今回は BMI を分類に
使わなかった。BMI に応じてコメントのトーンを調整するなどは今後の拡張余地とする。

## 3. コメントの事前生成（レシピ適応型の疎生成）

「カテゴリ × 全レシピ」を総当たりで生成すると、多くが無駄になる。たとえば鉄分が要点でない
レシピに貧血向けコメントを作っても、一般コメントとほぼ同じものになる。

そこで、レシピごとに LLM を1回呼び、「このレシピで専用コメントを出す価値がある病態カテゴリだけを
選び、そのコメントを書く（general は必ず、簡単なレシピなら手軽さの一言も）」という形にした。
レシピの素材に応じて LLM が効くカテゴリを判断するため、たとえば肉と野菜の炒め物では貧血・便秘が
選ばれ、揚げ物寄りのレシピでは脂質が選ばれる、というように生成対象が変わる。

結果、生成は205件に収まった。仮に当初検討した「病態カテゴリ × スキル2段階 × 全レシピ」を
総当たりで生成すると約700件、スキルをカテゴリにせず「病態 × 全レシピ」総当たりにしても約350件に
なる。これに対し、(1) スキルをカテゴリにせず beginner の有無で表現したこと、(2) レシピごとに
効くカテゴリだけを生成したこと、の2点で205件まで抑えた。LLM の呼び出し回数はレシピ数（50回）の
ままなので、API コストも増えていない。

### LLM に渡すレシピ情報

| 渡したもの | 理由 |
|---|---|
| レシピ名 | コメントの主語になる |
| 材料名（一覧） | 栄養的な訴求ポイント（鉄分・食物繊維・脂質など）の判断材料 |
| タグ（栄養価・調理時間など） | 塩分控えめ・手軽さなど、カテゴリ別の差が出やすい情報 |
| 手順数 | 簡単さの判断材料（`beginner` コメントの要否） |

手順本文や分量の詳細は渡していない。タグと材料名で栄養・調理の要点はカバーでき、
トークン数を抑えつつ必要な出し分けができると判断した。

### 生成を LLM に委ねることへの備え

カテゴリの選定を LLM に任せる以上、判断ミスが出力に直結する。これに対して次の対策を入れた。

- 安全リスクのある病態（透析・CKD 等）は分類段階で general に固定し、そもそも LLM の選択肢に入れない。
- general コメントは必ず生成させ、フォールバックの土台にする。
- 返ってきた JSON を検証し、想定外のカテゴリ名は捨てる。

## 4. リクエスト時のコメント取得

1. ユーザーの病態カテゴリのコメントがあればそれをベースにする。
2. なければ general。
3. それもなければ固定文（`このレシピをぜひお楽しみください。`）。

さらに、初級・初心者ユーザー かつ そのレシピに手軽さコメント（`beginner`）があるときは、
ベースのコメントの後ろに手軽さの一言を連結する。これにより「減塩の話＋手軽さ」のように、
病態とスキルの両方を反映したコメントになる。

存在しない `user_id` の場合もエラーにせず、固定文を返す。

## 5. データ整合性について

分類辞書の病態表記を、実データ（`users.csv`）の表記と突き合わせて確認した。
一部の病態（CKD・潰瘍性大腸炎）でカッコや数字の全角・半角がずれており、そのままでは
安全のための general 固定が効かない状態だったため、データ側の表記に統一して修正した。

## 6. 限界と今後

- 手軽さの一言は、ベースのコメントに連結する方式のため、文のつながりがやや機械的になる場合がある。
  生成段階で病態と手軽さを一体の文として書かせれば、より自然にできる。
- カテゴリの選定を LLM に委ねているため、本来効くはずの病態を取りこぼす可能性がある。
  重要な病態については、生成結果を確認する仕組みがあるとより安全。
- BMI は今回カテゴリに使っていない（§2.4 参照）。必要なら、同じ病態の中で BMI に応じて
  トーンを変えるなどの拡張が考えられる。
